Sandboxing Agent Code Execution: Containers, gVisor and Firecracker MicroVMs

Sandboxing agent code execution starts with one rule: treat generated code as untrusted. Match the isolation boundary to what the agent can reach.

For teams shipping coding and data-analysis agents, the same moment tends to repeat. Someone demos an agent that writes a Python script, runs it, reads the output and fixes its own bug. Everyone is delighted. Then a security engineer asks a question: where does that script run? The answer, more often than anyone likes, is “in the same container as the agent”, or “on the worker node, in a subprocess”.

That answer is the whole problem. The moment an agent executes code, you have a system that takes text from a model, text that was shaped by a user prompt, a retrieved web page, a PDF, a tool result, and turns it into instructions your CPU will follow. The model does not have to be malicious for this to go wrong. It only has to be persuadable, and persuadability is a property of every current model to some degree, open or closed.

There is plenty written about the policy side: allow-lists, approvals, output filtering. This piece is about the layer underneath, the runtime boundary that still holds when the policy layer has been talked around. The argument is short. Treat agent-run code as untrusted input, the way you would treat a file uploaded by an anonymous user. Pick the isolation boundary to match what that code can reach. And accept that stronger isolation costs you startup time, because that is decent enough tradeoff.

Key Takeaways
  • Code an agent generates is untrusted input, whichever model wrote it. Design the runtime as if the code were hostile.
  • A plain container shares the host kernel. That is fine for low-risk work and a thin boundary for anything touching secrets, customer data or the network.
  • gVisor puts a user-space kernel between code and host. Firecracker puts a hardware-virtualized microVM there. Each buys isolation and charges you in startup time, compatibility or density.
  • Choose the boundary by blast radius, not by habit. The business question is what a single escape costs you, and whether a faster cold start is worth that exposure.

Why this is a different problem from a normal workload

Most of the isolation advice in the container world assumes you wrote the code you are running, or at least that a human reviewed it. Multi-tenant platforms have always been the exception, and they have always been the hard case. An agent that runs code turns your internal platform into a multi-tenant platform where the tenant is a statistical text generator with a very long attack surface.

Three properties make it worse than ordinary untrusted code.

First, the author is steerable by third parties. A web page the agent browses can contain instructions. A support ticket can too. The code that comes out is a function of inputs you do not control.

Second, the code is novel every time. You cannot scan it ahead of time against a known-bad list, because it did not exist until a second ago. Static review does not scale to thousands of generated snippets per hour.

Third, the agent is usually generous with capabilities. It has a filesystem, a network, environment variables with API keys, sometimes a cloud metadata endpoint. An escape is not just a curiosity; it lands next to things that matter.

The three boundaries, in plain terms

There are three common ways to draw the line between generated code and your host. They differ in what is shared.

Shared-kernel containers

A standard container, whether Docker, containerd or a Kubernetes pod, is a process on the host kernel with its namespaces, cgroups, capability drops and a seccomp profile. All of the code inside makes system calls straight to the host kernel. The kernel is the boundary.

That is a large boundary. The Linux system call interface is big, and kernel bugs that turn an unprivileged syscall sequence into host access are discovered with some regularity. Seccomp profiles shrink the exposed surface, and a tight profile is a real control. But you are betting that the remaining surface has no exploitable flaw, and that your profile is correct for every library the agent might import.

Where plain containers still make sense: code that runs against synthetic data, with no network, no secrets, short-lived, in a throwaway cluster that holds nothing of value. A scratch calculator for the agent, a formatter, a linter. The blast radius of an escape is small, so a thin boundary is a reasonable choice.

gVisor: a user-space kernel

gVisor, shipped as the OCI runtime runsc, takes a different approach. It is an application kernel written in Go that runs in user space. Per the project’s documentation, its main component, the Sentry, implements system calls, signal delivery, memory management and the threading model itself, rather than passing them to the host kernel. File access that has to leave the sandbox goes through a separate process called the Gofer, and the Sentry runs under a restricted seccomp profile with no direct filesystem access.

The effect is that the generated code is talking to a reimplementation of Linux, and only a small, filtered set of host calls is ever made on its behalf. A kernel bug in the host’s filesystem or networking code is much harder to reach, because the code never gets to call those paths directly.

It plugs into Docker and Kubernetes as a runtime, so adoption is a runtime class change rather than a re-architecture. That is a big part of its appeal.

The costs are the ones the gVisor docs state themselves. It does not implement every system call, /proc file or /sys file, so some software will not run as is. Intercepting system calls adds per-call overhead, and the project notes it may perform poorly on syscall-heavy workloads. For an agent running a pandas script, the overhead is usually invisible. For one compiling a large codebase or hammering the filesystem, you will feel it.

Firecracker microVMs: a hardware boundary

Firecracker is a virtual machine monitor from AWS that uses the Linux KVM interface to run lightweight virtual machines. It is the technology behind AWS Lambda, and sandbox products built for agents, E2B among them, use it too. Each workload gets its own guest kernel running behind hardware virtualization.

The attack surface is deliberately small. The Firecracker project emulates only a short list of devices: virtio-net, virtio-block, virtio-vsock, virtio-balloon, a serial console and a minimal keyboard controller used to stop the microVM (see the Firecracker design document and its device docs). Compare that with a general-purpose VM monitor and you can see the design intent: strip everything the guest does not need.

The project’s own figures are a boot in under 125 ms and under 5 MiB of memory overhead per microVM, with up to 150 microVMs created per second per host. Those are vendor numbers, measured under the project’s own conditions, and your results will vary with kernel, root filesystem and what you do after boot. Treat them as an indication of order of magnitude, not a promise.

What you get is a boundary where an exploit has to break out of a guest kernel and then the hypervisor interface, not just a syscall filter. What you pay is a guest kernel to boot, a root filesystem to provide, and a slightly more involved operational story, because microVMs do not drop into a Kubernetes pod spec as neatly as a runtime class does. Projects like Kata Containers bridge some of that gap by running pods inside lightweight VMs, and they can use Firecracker as one of their backends.

Cold start is the price, and you can pay it deliberately

The agents might feel slow when each step waits on a fresh sandbox. A user watching a spinner while a microVM boots will blame the product, not the security design. That pressure is how teams end up reusing one long-lived container for every task, which is the worst of both worlds: a thin boundary and shared state between runs.

There are ways to reduce the cost without giving up the boundary.

Warm pools. Keep a pool of pre-booted sandboxes and hand one to each session. You pay memory for idle capacity and gain near-zero perceived start. The rule that matters: a sandbox is used by one session and then destroyed, never recycled to a different tenant.

Snapshots. Firecracker supports snapshotting a microVM, so you can boot once, install your interpreter and common libraries, snapshot, and restore from that point. This trades boot time for restore time and some operational care. Check the current snapshot documentation for the security caveats around restoring multiple clones from one snapshot, such as duplicated random state, before you rely on it.

Tier by task. Not every step needs the strongest boundary. Route by risk: pure computation on provided data goes to the cheaper tier; anything that touches credentials, mounts a volume or opens the network goes to the stronger one. This is the point of the diagram above, applied at runtime.

Session scope. Keep one sandbox per conversation or task rather than per command. Cold start is amortized across many steps, and state within the session still dies with it.

What the boundary does not cover

A sandbox is a runtime control, and it fails if the surrounding configuration undermines it. The most common failures have nothing to do with the isolation technology.

  • Secrets inside the sandbox. If the agent’s API keys are in environment variables in the sandbox, an escape is unnecessary. The code can just read and send them. Keep credentials outside and let a proxy inject them per request.
  • Open egress. An isolated process that can reach any host can still exfiltrate anything it was given. Default-deny the network, then allow named destinations.
  • Cloud metadata and internal services. Block link-local metadata endpoints and your internal network ranges from the sandbox. A boundary that keeps the code off the host is little use if it can call an internal admin API.
  • Writable shared mounts. A volume mounted into several sandboxes is a side channel and a persistence mechanism. Prefer per-session scratch space and copy artifacts out through a controlled path.
  • No resource limits. CPU, memory, process count and wall-clock time need ceilings. A fork bomb is not an exotic attack; sometimes it is just a model trying something.
  • Host-side parsing of output. What comes back out of the sandbox is also untrusted. Treat it as data, and do not feed it to a shell or template engine on the trusted side.

For the policy layer that decides what the agent is allowed to attempt, the earlier piece on layered prompt-injection controls covers it. The sandbox is what you are left with when that layer has been defeated, so it should assume it will be.

A decision framework to implement this

Work through four questions, in order, and let the first “yes” set the minimum tier.

  1. Does the code have access to secrets, production credentials or customer data? Yes means a microVM, or a hardware-virtualized equivalent. This woudl come with the extra startup time
  2. Can it reach the network beyond a short allow-list? Yes means at least a user-space kernel, and probably a microVM, because exfiltration and lateral movement become part of the threat.
  3. Does it run multiple tenants or users on the same host? Yes means do not use a shared-kernel container as the only boundary.
  4. Is it single-tenant, no secrets, no network, short-lived? A hardened container with a tight seccomp profile, dropped capabilities, read-only root and resource limits is a defensible choice.

Notice that none of these questions mention the model. That is deliberate. The same boundary applies whether you call a frontier API, run an open-weights model on your own GPUs, or mix both. Where the model runs affects your data governance and cost; where the generated code runs is a separate decision with its own risk. Teams that self-host their model sometimes assume the whole stack is therefore “inside the perimeter” and skip the sandbox. The generated code is just as untrusted there.

The executive view

For a business leader, this is a question of exposure per dollar. The levers are concrete.

  • Blast radius. Ask what an escape reaches in your environment. If the answer is “our production network”, the boundary should be the strongest you can operate.
  • Latency budget. Ask what cold start the user experience can absorb, then see whether warm pools and snapshots close the gap before you weaken the boundary. Most of the time they do.
  • Operational ownership. MicroVMs and user-space kernels need someone who understands them. A managed sandbox service moves that burden to a vendor, at a price and with a dependency. Running your own gives you control and puts patching, capacity planning and incident response on your team. Both are legitimate; the right choice depends on whether you have the platform engineers to run it well.
  • Evidence for auditors. A documented isolation tier per task class, with the reasoning, is something you can show a customer’s security review. “We run it in a container” is not.

Where I would start

If you have an agent executing code today and have not thought about this, do three things before the next release. Move the code execution out of the agent’s own process and container. Remove every credential from the environment the code runs in and default-deny its network. Then pick a tier from the four questions above and write down why.

After that, measure. Time the cold start of each option with your real interpreter image and your real dependencies, not the vendor’s headline figures. Test whether your common libraries run under gVisor. Check what a warm pool costs you in idle memory. Those three numbers turn a security argument into a budget conversation, and budget conversations are the ones that actually get a boundary funded.

The agent is going to run code. The only decision you control is how much of your infrastructure that code gets to touch when it behaves badly.
